### SEC-003 — JWT signing secret silently falls back to a public placeholder value  [FIXED (2026-07-24)]
- **Source:** `code-review/audit-security` (backend), must-fix (hardcoded-secret)
- **Tier rule matched:** `hardcoded-secret` → BLOCKING
- **Location:** `apps/backend/src/config.ts:7` — `jwtSecret: process.env.ADMIN_JWT_SECRET ?? "dev-only-change-me"`
- **Why blocking:** Verified by direct read. If `ADMIN_JWT_SECRET` is ever unset or empty in a deployed environment, the server boots normally and signs/verifies every session token with a publicly-known literal string — anyone could forge a SUPER_ADMIN token. No startup check exists anywhere in `index.ts`/`app.ts`/`config.ts` that fails fast on this.
- **Suggested fix:** At process start, validate `ADMIN_JWT_SECRET` is present, has sufficient entropy (≥32 bytes), and is not a known placeholder; `process.exit(1)` with a clear log line otherwise. Remove the fallback default entirely.
- **Status:** FIXED (2026-07-24) — added `resolveJwtSecret()` (`config.ts`): throws at startup in production if `ADMIN_JWT_SECRET` is unset, under 32 characters, or a known placeholder; dev/test keeps the `dev-only-change-me` fallback. Regression tests: `config.test.ts` (6 cases). Commit `ba7e22c`.
- **Note (2026-08-06):** Now moot in this repo: `resolveJwtSecret`, `config.jwtSecret` and `config.cookieName` were deleted with the Apps Gateway migration, along with `JWT_SECRET`/`COOKIE_NAME` from `.env.example`, `docker-compose.yml`, CI and the k8s docs. This app signs nothing and verifies nothing — the gateway authenticates at the edge and forwards the user email in `X-User-Id`, so there is no secret left to fall back to. The equivalent guard and its regression tests still exist in `bliblitalk-user-fe`, which does still issue participant sessions.

### SEC-005 — No rate limiting anywhere in the API  [FIXED (2026-07-24)]
- **Source:** `code-review/audit-security` (backend), must-fix
- **Tier rule matched:** `must-fix` → BLOCKING
- **Location:** `apps/backend/src/app.ts` (no rate-limit middleware mounted); `apps/backend/package.json` (no `express-rate-limit` or equivalent dependency)
- **Why blocking:** Confirmed absent from `app.ts` and `package.json`. `/api/auth/login`, `/register`, `/google`, and the SEC-001/002 bypass endpoints can be hit at unlimited request rates — unrestricted brute force against bcrypt hashes and unrestricted email enumeration via `/auth/google`'s registered/unregistered oracle and `/auth/register`'s `EMAIL_TAKEN` 409.
- **Suggested fix:** Add a per-IP + per-identifier limiter in front of `/api/auth/*` at minimum (e.g. `express-rate-limit`), mounted before the auth router, returning 429 with `RateLimit-*` headers.
- **Status:** FIXED (2026-07-24) — added `createAuthRateLimiter()` (`middleware/rateLimit.ts`, factory so each `createApp()` gets an independent store), mounted in front of `/api/auth` in `app.ts`: 50 requests / 15 min per IP, 429 with `RateLimit-*` headers. Regression tests: `rateLimit.test.ts` (2 cases). Commit `108b670`. **Follow-up (144283f):** a re-audit found the limiter's per-IP bucketing was defeated by the documented single-reverse-proxy deployment topology (`k8s/README.md`) — `req.ip` would resolve to the proxy's own address for every client, collapsing everyone into one shared bucket. Added `app.set("trust proxy", 1)`; regression test `app.test.ts` ("SEC-005 follow-up: rate limit buckets by the real client IP...").
- **Note (2026-08-06):** The limiter survived the Apps Gateway migration but changed both role and target. `createAuthRateLimiter()` became `createAdminApiRateLimiter()` and now guards `/api/admin` at 600 requests / 15 min per IP. The endpoints the original finding named no longer exist — there is no login, no bcrypt comparison and no email-enumeration oracle left in this app to brute-force, and the gateway refuses unauthenticated traffic before it reaches us. What remains is a blast-radius cap on an authenticated caller, which is why the ceiling is deliberately generous rather than tight. `trust proxy` and its regression test are unchanged; `app.test.ts` now drives `/api/admin/dashboard` instead of the deleted `/api/auth/me`.

### SEC-006 — Session cookie (JWT) is logged in cleartext on every request  [FIXED (2026-07-24)]
- **Source:** `code-review/audit-security` (backend), must-fix
- **Tier rule matched:** `must-fix` → BLOCKING
- **Location:** `apps/backend/src/app.ts:35` — `app.use(pinoHttp({ logger }))`, no `redact` option
- **Why blocking:** Confirmed by direct read — `pino-http`'s default request serializer logs `req.headers` verbatim, including `Cookie`. Every request's session JWT (role/email claims) is written to application logs in cleartext; anyone with log access can lift and replay any user's session, including admins.
- **Suggested fix:** `pino-http({ logger, redact: ["req.headers.cookie", "req.headers.authorization"] })`, or a custom serializer that strips those headers.
- **Status:** FIXED (2026-07-24) — `createRequestLogger()` (`app.ts`) passes `redact: LOG_REDACT_PATHS` to `pino-http`, covering `req.headers.cookie`, `req.headers.authorization`, **and** `res.headers["set-cookie"]`. The response-side redaction was added in a follow-up commit after a re-audit caught that a login/register response's own freshly-issued `Set-Cookie` header still leaked into logs (the request-only fix in `61c4de9` was incomplete). Regression tests: `app.test.ts` ("never writes a request's session cookie to the logs", "SEC-006: never writes a response's session cookie (Set-Cookie) to the logs"). Commits `61c4de9`, `144283f`.

- **Why blocking:** Verified against HEAD 2026-08-12 — `helmet` is absent from both repos' dependencies and no hand-written header middleware exists, so no response carries `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` or a frame-ancestors restriction, and `x-powered-by` is left on. - **Status:** FIXED (2026-08-13) — `helmet@8.3.0` mounted as the first middleware in `createApp`, together with `app.disable("x-powered-by")` and an explicit `nosniff` handler on the `/api/uploads` static route (`apps/backend/src/middleware/securityHeaders.ts`, `app.ts:45-52,78`).   - **Two documented deviations from the suggested policy.** `script-src` is `'self'` with no nonce: the built `index.html` was checked and contains exactly one external module script and no inline script, so a nonce would add machinery without adding a control. `img-src` is `'self' data: https:` rather than `'self' data:` — `bannerUrl`/`thumbnailUrl`/speaker photos are free-text fields (`packages/shared-types/src/schemas.ts:231-232,465-466`, see SEC-012) that admins routinely point at external hosts, so `'self'` would blank out existing content; `https:` still blocks mixed content, and images are not an execution context. `style-src` keeps `'unsafe-inline'` because components use React `style={{}}` attributes; removing them is a UI refactor, not a security fix.
  - **Known consequence:** `frame-src` falls back to `default-src 'self'`, so an embedded third-party player (e.g. YouTube for `recordingUrl`) would be blocked. No `<iframe>` exists in either frontend today — grep-verified — but whoever adds one must widen `frame-src` deliberately rather than discover it as a bug.
  - HSTS is deliberately **not** set here: TLS terminates at Apps Gateway, so the header belongs at that edge.

### SEC-023 — Rate limiter's in-memory store won't scale across multiple replicas  [OPEN]
- **Source:** `code-review/audit-security` (backend re-audit, 2026-07-24), should-fix
- **Tier rule matched:** `should-fix` → ADVISORY
- **Location:** `apps/backend/src/middleware/rateLimit.ts` — `createAuthRateLimiter()` uses `express-rate-limit`'s default in-memory store
- **Why advisory:** Not exploitable today — `k8s/README.md`'s "2+ replicas" topology is documented intent only; no manifests are wired yet and nothing is deployed (confirmed local-only). Once real replicas exist, each keeps an independent counter, so effective attacker/legitimate-user capacity multiplies with replica count, quietly weakening the SEC-005 rate limit.
- **Suggested fix:** Before scaling `bliblitalk-admin` past a single replica, switch `createAuthRateLimiter()` to a shared store (e.g. Redis via `rate-limit-redis`) so the limit is enforced cluster-wide.
- **Status:** OPEN
- **Note (2026-08-12) — re-tiered ADVISORY → BLOCKING by external review.** The Information Security review of 2026-08-11 records this same defect as its Finding 9 (Medium severity, Medium confidence) and adds a second dimension the original entry did not cover: `app.ts:45` sets `trust proxy 1`, so `req.ip` is taken as the second-to-last `X-Forwarded-For` entry — a hop count that **cannot be verified from this repo**, because no Ingress/Service manifest exists and `docker-compose.yml` publishes the port with no proxy at all. Extended fix: move the limiter to a shared store (`rate-limit-redis`), **and** make the hop count verifiable — commit the real Ingress/Service manifests and assert the resolved `req.ip` in a startup log line so a wrong `trust proxy` value is visible in an environment instead of silently changing behaviour.
